# مسار — دليل الإعداد والنشر

هذا التطبيق واجهة أمامية ثابتة (تصلح لـ GitHub Pages) متصلة بـ **Supabase** كـ Backend
حقيقي: قاعدة بيانات Postgres، مصادقة حقيقية (تشفير كلمة المرور بـ bcrypt من
جهة الخادم)، وجلسة JWT — بدل التخزين المحلي الوهمي في النسخة الأصلية.

## لماذا Supabase تحديداً؟

GitHub Pages يستضيف ملفات ثابتة فقط ولا يقدر يشغّل سيرفر أو قاعدة بيانات.
Supabase يعطيك قاعدة بيانات Postgres حقيقية + نظام مصادقة حقيقي عبر REST
API تستدعيه الواجهة الأمامية مباشرة من المتصفح — فتحصل على "Backend حقيقي"
مع بقاء الاستضافة على GitHub Pages بدون أي تغيير.

## خطوات الإعداد (مرة واحدة)

1. أنشئ حساباً مجانياً على [supabase.com](https://supabase.com) ثم مشروعاً جديداً.
2. من **SQL Editor** داخل لوحة تحكم المشروع، افتح استعلاماً جديداً، الصق
   محتوى ملف `schema.sql` المرفق، وشغّله. هذا ينشئ الجداول الأربعة
   (`profiles`, `income`, `expenses`, `goals`) مع تفعيل **Row Level
   Security** بحيث لا يقدر أي مستخدم يشوف أو يعدّل بيانات غيره — الحماية
   تُفرض من قاعدة البيانات نفسها، مو من كود الواجهة.
3. من **Project Settings → API**، انسخ:
   - `Project URL`
   - `anon public` key (هذا المفتاح **مصمّم ليكون علنياً** — الحماية
     الفعلية تأتي من RLS في الخطوة السابقة، وليس من إخفاء هذا المفتاح)
4. انسخ `config.example.js` باسم `config.js` وضع فيهما القيمتين أعلاه.
5. (اختياري، لكن يُنصح به) من **Authentication → Providers → Email**، عطّل
   "Confirm email" أثناء التطوير حتى يدخل المستخدم مباشرة بعد التسجيل بدون
   انتظار بريد تأكيد. فعّلها قبل الإطلاق الفعلي للمستخدمين الحقيقيين.

## النشر على GitHub Pages

ارفع هذا المجلد بالكامل — **بما فيه `config.js`** — إلى مستودعك، ثم فعّل
GitHub Pages من إعدادات المستودع (Settings → Pages) على الفرع المناسب.
لا حاجة لأي بناء (build) أو خطوة إضافية؛ الملفات ثابتة بالكامل.

> يجب رفع `config.js` مع بقية الملفات ليعمل الموقع على GitHub Pages —
> لأنه استضافة ثابتة تخدم بالضبط ما هو موجود بالمستودع. هذا آمن لأن
> `anon public` key وحده لا يعطي أي صلاحية دون المرور بسياسات RLS.

## أخطاء شائعة أثناء الاختبار

- **`profiles` insert فشل بـ 400 عند التسجيل**: كان هذا خللاً في الإصدار
  الأول — إنشاء صف `profiles` كان يتم من كود الواجهة الأمامية مباشرة بعد
  `signUp()`، لكن إذا كان "Confirm email" مفعّلاً في مشروعك، لا توجد جلسة
  مصادقة فورية بعد التسجيل، فترفض سياسة RLS العملية. **الحل الحالي**: صف
  `profiles` يُنشأ تلقائياً بواسطة Trigger على مستوى قاعدة البيانات
  (`handle_new_user` في `schema.sql`) يعمل بصلاحيات مرتفعة كجزء من إنشاء
  المستخدم نفسه في `auth.users`، فيعمل بغض النظر عن حالة تأكيد البريد. إذا
  كنت شغّلت `schema.sql` قبل هذا التحديث، أعد تشغيله بالكامل — كل أوامره
  آمنة للتكرار (`if not exists` / `create or replace`).
- **"For security purposes, you can only request this after N seconds"**:
  ليس خطأً في الكود — هذا تحديد معدّل الطلبات المدمج في Supabase لحماية
  `signup`/`OTP` من إساءة الاستخدام. يظهر إذا حاولت التسجيل عدة مرات
  متتالية بفترة قصيرة. انتظر المدة المذكورة وحاول مرة أخرى.

## ما الذي تغيّر أمنياً ومعمارياً

- **XSS**: كل نص يدخله المستخدم (أسماء الدخل/المصاريف/الأهداف) يمر الآن
  عبر دالة `esc()` قبل إدراجه في الصفحة، فلا يقدر أي نص يحتوي وسوم HTML
  يُنفَّذ كسكربت.
- **onclick بمعطيات مستخدم**: النمط الخطير
  `onclick='app.x(${JSON.stringify(item)})'` أُزيل بالكامل، واستُبدل
  بـ Event Delegation: عنصر واحد فقط يستمع للنقر على مستوى الصفحة، ويقرأ
  `data-action` و`data-id` من العنصر المنقور عليه، ثم يبحث عن العنصر
  الفعلي في الحالة (state) بدل تمرير بياناته الخام داخل HTML.
- **المصادقة**: `sb.auth.signUp` / `signInWithPassword` من Supabase —
  كلمة المرور تُشفَّر بـ bcrypt على الخادم ولا تُخزَّن أبداً كنص صريح في
  الواجهة، والجلسة عبارة عن JWT يديره SDK تلقائياً.
- **تعديل المصاريف دون الكتابة فوق التاريخ المالي**: كل عنصر دخل/مصروف
  يحمل مصفوفة `revisions`. إذا عدّلت المبلغ/الاسم/التصنيف بعد مرور وقت
  عليه، يُضاف تعديل جديد بتاريخ سريانه (`effectiveMonthIdx`) بدل الكتابة
  فوق القيمة الأصلية — فحسابات الأشهر الماضية تبقى كما كانت فعلاً وقتها،
  بينما الشهر الحالي والمستقبل يعكسان القيمة الجديدة.
- **Routing حقيقي**: الرابط (`#/dashboard`, `#/income`, ...) هو المصدر
  الوحيد لتحديد الشاشة المعروضة، فأزرار الرجوع/التقدم في المتصفح تعمل
  بشكل صحيح ويمكن مشاركة رابط مباشر لأي صفحة.

## وضع المعاينة التجريبي (بدون حساب)

زر "تجربة بحساب توضيحي جاهز" في شاشة الدخول يفتح بيانات وهمية محلية
بالكامل (لا تُحفظ ولا تلمس Supabase) لتجربة الواجهة بسرعة. أي تعديل فيه
يختفي عند تحديث الصفحة — وهذا مقصود وواضح للمستخدم عبر تنبيه عند الدخول.

## ملاحظة حول الأمان

لا يوجد نظام "آمن 100%" — لكن مع RLS مفعّلة وكلمات المرور مُدارة بالكامل
من طرف Supabase، لم يعد أي جزء من "المصادقة الحقيقية" يعتمد على كود
يعمل في متصفح المستخدم. راجع [توثيق Supabase RLS](https://supabase.com/docs/guides/database/postgres/row-level-security)
للتوسع لاحقاً (مثل: تحديد معدل الطلبات، تدقيق أعمق على الحقول).
